# 概念边界

这三个名称是工程实践中对不同缓存失效模式的归纳，不是 Redis 服务端的三个错误码。
判断时要看影响范围、请求的数据是否存在，以及回源请求是否围绕单个热点 Key。

## 缓存雪崩

缓存雪崩指大量 Key 在接近的时间失效，或整个缓存层暂时不可用，导致大量请求同时回源到数据库或下游服务。
核心特征是影响的 Key 范围广，流量峰值可能压垮下游。

常见缓解方法包括：在 TTL 上增加随机抖动，避免大批 Key 同时过期；对回源路径进行限流、排队和降级；
对核心数据预热；监控命中率、过期量和下游负载；对 Redis 部署做高可用与故障演练。

## 缓存击穿

缓存击穿通常是单个高频热点 Key 失效。许多并发请求在同一时刻发现未命中，然后重复回源并重建同一份数据。
英文资料常称为 cache stampede 或 thundering herd。

常见缓解方法是 single-flight/request coalescing：只允许一个请求回源重建，其他请求等待或复用结果。
也可以使用带超时的互斥锁、逻辑过期、提前刷新和热点预热。锁必须有超时、所有者标识和安全释放逻辑，避免死锁或误删他人的锁。

## 缓存穿透

缓存穿透指请求持续查询本来就不存在的数据。由于缓存和数据库都无法返回正常对象，如果应用不记录这类结果，每次请求都会穿过缓存访问下游。

常见缓解方法包括：在合理的短 TTL 内缓存“不存在”结果；在请求入口做格式、范围和权限校验；
使用布隆过滤器快速判断某个标识肯定不在集合中；对异常未命中率进行限流和告警。
布隆过滤器存在假阳性，应用仍需处理实际数据不存在的情况。

# 快速区分

- 大量 Key 或整个缓存层出现问题：优先按雪崩排查。
- 单个热点 Key 过期后并发回源：优先按击穿排查。
- 请求的数据在业务上本来就不存在：优先按穿透排查。
