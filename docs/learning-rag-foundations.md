# SupportPilot RAG 基础与代码地图

## 一条问题如何得到答案

RAG 的完整链路是：

```text
离线阶段：文档 -> 清洗 -> 切块 -> 索引
在线阶段：用户问题 -> 检索 -> 重排 -> 生成并引用证据
```

前三步决定“知识库里有什么、知识边界在哪里”，索引决定“如何快速找到”，检索和重排决定“给模型看什么”，生成决定“如何基于证据组织答案”。大模型并不会因为接入了 RAG 就自动知道 Redis 文档；它只能看到当前请求中检索出来的少量 chunk。

在本项目中的对应关系：

- `app/ingestion/markdown.py`：解析和清洗；
- `app/ingestion/chunking.py`：章节识别和切块；
- `app/ingestion/pipeline.py`：校验输入、生成产物和统计；
- `data/processed/chunks.jsonl`：等待建立索引的标准数据。

## chunk、metadata 和 embedding

### chunk

chunk 是从大文档中切出的、可以独立参与检索的最小证据单元。例如 `Redis persistence` 很长，RAG 不应把全文都发给模型，而应召回 `Append-only file > How durable is the append only file?` 对应的几段。

切得太大，会混入无关内容、占用上下文；切得太小，会丢失因果关系和上下文。450 只是第一版实验参数，不能把它当成固定真理。

### metadata

metadata 是描述 chunk 的结构化信息，不是主要答案正文。本项目保存标题、章节路径、原始文件、官网 URL、目标版本、文档类型和片段序号。

metadata 有三个用途：

1. 给检索结果补足语境，例如正文只有 `username`，但标题和章节表明它是 `ACL GETUSER > Required arguments`；
2. 过滤，例如只查 Redis 7.4 或 command 文档；
3. 引用和排错，回答可以链接原文，召回错误时也能找到源文件。

### embedding

embedding 是模型把文本转换成的一串浮点数，也叫向量。语义相近的文本通常在向量空间中距离更近。因此“Redis 为什么变慢了”和“latency spikes”即使没有完全相同的单词，也可能互相召回。

embedding 不是摘要，不直接回答问题，也不是把知识训练进大模型。它只是供相似度搜索使用的数值表示。模型、向量维数和文本预处理方式变化后，索引通常需要重建。

## 为什么保留标题和来源

标题是语义的一部分。正文 `Simple string reply: OK` 本身几乎没有检索价值，加上 `REPLICAOF > Return information` 后才知道它在描述哪个命令。

来源用于：

- 向用户提供可核验引用；
- 区分官网事实和模型生成文字；
- 发现错误时回到原文；
- 防止不同产品、版本的内容混淆；
- 支持更新文档后只重建受影响的数据。

因此后续通常用 `标题 + 章节路径 + content` 形成检索文本，但只把 `content` 当作证据正文展示。

## 关键词检索与向量检索

关键词检索（本项目后续使用 BM25）依赖词项是否出现，并根据词频和稀有度打分。它擅长精确命令、配置名、报错和专有名词，例如 `appendfsync`、`NOAUTH`、`cluster_state:fail`，速度快且容易解释；缺点是同义表达可能匹配不到。

向量检索比较 embedding 的语义距离。它擅长自然语言改写和中英文语义，例如“数据断电后会丢多少”匹配 AOF durability；缺点是可能召回语义看似接近但事实不相关的段落，对精确字符串有时反而不如 BM25。

两者不是二选一。本项目将先做 BM25 基线，再做向量检索，最后融合两路候选。只有评测证明融合有收益，才保留复杂方案。

## 检索和重排的区别

检索从全部 chunk 中快速找出一小批候选，例如从 423 个中找出 20 个。它必须快，判断通常较粗。

重排器对“问题—候选 chunk”逐对进行更精细的相关性判断，把最能回答问题的证据排到前面，例如把 20 个候选重排后取前 5 个交给生成模型。重排改善排序，但无法找回第一阶段完全漏掉的证据。

## 为什么先建评测集

没有固定问题和标准证据时，调整 `chunk size`、`top_k` 或融合权重只是在凭感觉看几个例子，很容易挑到对自己方案有利的案例。

评测集应先记录真实问题、期望来源、必要答案点和是否应拒答。然后每次只修改一个变量，在同一批问题上比较 Recall、延迟和失败案例。评测集不是绝对真理，也要持续审查，但它让优化从“感觉更好”变成“证据显示更好”。

评测集还应包括：自然语言问题、精确命令问题、多跳问题、无答案问题，以及容易与 Redis 8/Cloud 混淆的问题。

## Recall@K

Recall@K 检查标准相关证据是否出现在检索结果前 K 名中。单个问题只有一个标准证据时：

```text
前 K 个结果含标准证据 -> 1
前 K 个结果不含标准证据 -> 0
```

例如 20 道题中有 16 道在前 5 个结果里找到正确证据，则问题级 Recall@5 为 `16 / 20 = 80%`。

如果一道题标注多个必要证据，可使用：

```text
Recall@K = 前 K 个结果命中的标准证据数 / 标准证据总数
```

Recall@K 只评价“有没有找回来”，不保证第一名最好，也不评价最终回答是否正确。因此后续还需要排名指标、引用准确性和答案评测。选择 K 也有代价：K 越大通常 Recall 越高，但会增加重排延迟、上下文噪声和模型成本。
